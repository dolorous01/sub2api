# Sub2API Infinite Canvas 图片生成设计

日期：2026-08-02

状态：已批准，待实施计划

范围：用户与管理员图片生成入口、Infinite Canvas 微前端、全站图片模型链、服务端画布持久化、模型回退与实际模型计费

上游基线：`basketikun/infinite-canvas@ea0414e88cffa6b522cc13c0613b3c8085983a53`

## 1. 背景

Sub2API 当前使用 Vue 3 前端和 Go 后端，并已提供 OpenAI 兼容图片端点：

- `POST /v1/images/generations`
- `POST /v1/images/edits`

现有图片路径已经承担鉴权、账号调度、故障转移、用量记录和计费。另有已批准的异步图片任务设计：

- `docs/superpowers/specs/2026-07-24-async-images-codex-design.md`

本设计在该服务端能力之上增加完整的无限画布产品体验。用户要求在用户端和管理端左侧导航中都增加“图片生成”，由管理员维护全站图片模型顺序，用户可从该顺序中选择一个优先模型，服务故障时再按管理员顺序回退。

上游 `basketikun/infinite-canvas` 是 React、TypeScript、Vite 和 Zustand 应用。它默认把 Provider URL 和 API Key 保存在浏览器并直接调用图片 Provider。该模式不能直接用于 Sub2API，因为它会绕过 Sub2API 的权限、额度、账号调度、审计和计费。

上游采用 AGPL-3.0。项目方已明确接受直接复用和修改上游源码时承担的 AGPL 义务。实际发布仍需进行许可证合规复核；本设计不是法律意见。

## 2. 目标

1. 在用户左侧导航增加 `/images`“图片生成”入口。
2. 在管理员左侧导航增加 `/admin/images`“图片生成”入口，包含生成画布和模型配置两个标签。
3. 保留上游完整无限画布的核心体验，包括项目、节点、缩放和平移、多选、连接、文生图、图片编辑、连续分支、导入和导出。
4. 以同源 React 微前端接入现有 Vue 应用，不使用 iframe，也不把上游 API Key 或 Provider URL 暴露给画布。
5. 由管理员维护一条全站有序图片模型链；第一项是主模型，其余项是可多选并排序的兜底模型。
6. 用户只能从管理员模型链中选择模型。用户所选模型优先，其余模型仍按管理员顺序回退。
7. 用户在画布中主动选择自己名下的 API Key，模型权限、分组调度、额度预占和账单都绑定该 Key。
8. 仅对服务故障触发模型回退；按最终成功模型和实际图片数量向用户结算一次。
9. 在服务端持久化画布项目、节点关系、任务和图片资产，使用户可跨设备继续编辑。
10. 通过异步任务避免长耗时生图阻塞浏览器或前置代理，并支持事件流和轮询恢复。
11. 保持现有同步 OpenAI 图片端点和其他 AI 功能兼容。
12. 提供 AGPL-3.0 要求的版权、许可证、修改声明和对应源码入口。

## 3. 非目标

- 第一版不实现多人实时协作、评论、公开分享或项目市场。
- 第一版不允许按用户组、套餐或单个用户覆盖模型链。
- 第一版不让用户输入任意模型名、Provider URL 或上游 API Key。
- 第一版不引入新的 GPU 推理服务，也不改变现有上游账号凭证管理方式。
- 第一版不自动重写提示词，也不使用文本模型决定图片模型顺序。
- 第一版不删除或改变 `/v1/images/generations` 和 `/v1/images/edits` 的同步行为。
- 第一版不把图片二进制或 Base64 存入 PostgreSQL。
- 第一版不在失败后自动降低图片尺寸、数量、质量或删减参数；这类行为会改变用户请求语义。
- 本设计不授权生产切流。实际 HAProxy 蓝绿切换仍需独立的维护窗口确认。

| 管理范围 | 全站统一模型链 |
| 回退顺序 | 管理员明确排序，依次尝试 |

| 许可证 | 接受 AGPL-3.0 合规要求 |

## 5. 已评估的接入方案

### 5.1 同源 React 微前端

保留上游 React 画布核心，将其构建为独立 chunk，由 Vue 宿主页面挂载。认证、模型策略、任务、存储和计费全部改走 Sub2API 后端。

优点：最大程度保留完整画布，迁移量可控，后续更容易对照上游更新。缺点：前端存在 Vue 与 React 两种运行时，需要明确构建和生命周期边界。

结论：采用。

### 5.2 完整迁移为 Vue

把 React/Zustand 画布重写为 Vue/Pinia。

优点：与 Sub2API 前端栈统一。缺点：初始迁移和回归风险最高，后续同步上游困难。

结论：不采用。

### 5.3 独立 iframe 应用

独立部署上游并在 Vue 页面嵌入 iframe。

优点：首次接入较快。缺点：登录桥接、焦点、路由、弹窗、下载、移动端和安全隔离更复杂，体验不一致。

结论：不采用。

## 6. 总体架构

实现分为六个清晰边界。

### 6.1 Vue Canvas Host

负责 Sub2API 路由、登录和管理员权限门禁、全局侧栏、主题与语言同步，以及 React 画布的挂载和销毁。宿主通过显式 `CanvasHostContext` 向微前端提供能力，不允许 React 代码直接依赖 Vue store。

```ts
interface CanvasHostContext {
  apiBaseURL: string
  locale: string
  theme: 'light' | 'dark'
  routeMode: 'user' | 'admin'
  navigate(path: string): void
  notify(level: 'success' | 'warning' | 'error', message: string): void
}
```

认证继续使用 Sub2API 现有同源 API 客户端约定。宿主不得把上游账号密钥、Provider URL 或管理员配置写入 URL、DOM 属性或画布持久化数据。

### 6.2 React Canvas App

从固定上游提交派生，负责无限画布、节点交互、项目操作、生成控制、任务进度和图片预览。删除或封闭上游的 Provider 设置、浏览器 API Key 存储和直连 `/v1/images/*` 逻辑，改用类型化的 Sub2API Canvas SDK。

React 微前端必须暴露稳定生命周期：

```ts
mountCanvas(element, context): CanvasHandle
CanvasHandle.updateContext(context)
CanvasHandle.unmount()
```

全局事件监听、快捷键、定时器、对象 URL 和任务订阅必须在 `unmount()` 时释放，避免在 Vue 路由切换后残留。

### 6.3 Canvas Project Service

负责项目 CRUD、画布快照、乐观并发、资产引用和所有权检查。服务端是跨设备恢复的事实来源；浏览器缓存只能作为尚未同步变更的短期恢复副本，不能覆盖更新的服务端版本。

### 6.4 Image Model Policy Service

负责读取和更新全站模型链、校验重复项与能力、生成策略版本、构造每次任务的实际尝试顺序，以及写入管理员审计记录。

### 6.5 Image Job Orchestrator

复用已批准异步图片任务设计中的规范化请求、执行器、对象存储、worker、任务状态和计费基础。画布 API 是面向登录用户的业务适配层，不另写一套上游图片协议。

### 6.6 Image Object Store

复用异步图片任务设计的私有 S3、R2 或兼容对象存储。数据库只保存对象键、MIME、尺寸、摘要、所有者、保留策略和派生关系。所有下载都通过鉴权端点或短时签名 URL，桶不得公开列举。

## 7. 前端路由与界面

### 7.1 用户端

- 新增 `/images` 路由和左侧“图片生成”菜单项。
- 菜单受 `image_canvas_enabled` 公共功能开关控制；关闭时路由返回功能不可用状态，而不是加载空画布。
- 画布使用除 Sub2API 全局导航外的完整可用区域，不套用普通数据卡片布局。
- 顶部紧凑工具栏提供项目切换、名称、保存状态、撤销、重做、缩放、适应视图、导入和导出。
- API Key 选择器只显示当前用户自己名下的可用 Key，不显示密钥明文；没有 Key 时显示前往 API Key 页面创建的空状态。
- 模型选择器只显示当前策略中同时被所选 API Key 分组允许、且对本次操作兼容的模型。
- 底部生成工具负责提示词、参考图、尺寸、数量和提交。
- 生成节点展示 `queued`、`running`、`falling_back`、`saving`、`completed`、`failed` 和 `canceled` 状态。
- 结果节点支持预览、下载、复制提示词、作为编辑输入和创建后续分支。

### 7.2 管理端

- 新增 `/admin/images` 路由和管理员左侧“图片生成”菜单项。
- 页面提供“生成画布”和“模型配置”两个标签。
- “生成画布”复用同一 React 微前端；项目仍属于当前管理员用户，不是全站共享项目。
- “模型配置”由原生 Vue 实现，使用有序列表。第一项明确标记为主模型，其余项标记为兜底模型。
- 管理员可添加、移除、启停和拖拽排序，并在保存前查看最终执行顺序与能力警告。
- 配置入口只对管理员开放，更新必须写入审计日志。

### 7.3 响应式与可访问性

- 桌面端保留全局侧栏，并提供可收起的项目面板。
- 移动端全局侧栏改为抽屉，画布工具栏收为图标菜单，生成控制使用底部面板。
- 使用项目已有图标库；不熟悉的图标必须有工具提示和可访问名称。
- 画布必须支持键盘、鼠标和触控；焦点不能被 React 宿主或全局侧栏锁死。
- 固定工具条、节点和计数器使用稳定尺寸，确保加载、回退和错误文案不会推动布局或遮挡画布内容。

## 8. 模型策略

### 8.1 配置结构

第一版只存在一条全站策略：

```json
{
  "version": 7,
  "enabled": true,
  "models": [
    { "model": "model-a", "enabled": true, "position": 0 },
    { "model": "model-b", "enabled": true, "position": 1 },
    { "model": "model-c", "enabled": true, "position": 2 }
  ]
}
```

`position=0` 的启用模型是主模型。保存必须满足：

- 至少有一个启用模型；
- 模型标识非空且不重复；
- position 连续且唯一；
- 每个模型至少有一个可调度账号或渠道声明图片能力；
- 能力未知时允许管理员保存为禁用项，但不能向用户暴露。

模型能力至少区分 generation、edit、多图输入、mask、最大输入图数、支持尺寸、最大 `n` 和可透传高级参数。服务端校验是事实来源，前端禁用只是交互辅助。

### 8.2 用户选择与实际顺序

用户只能提交当前启用链中被所选 API Key 分组允许的模型。后端对每次请求按以下规则构造顺序：

```text
attempts = [用户所选模型] + [管理员启用顺序中除所选模型外的模型]
attempts = 按所选 API Key 的分组权限和本次操作能力过滤后的 attempts
```

例如管理员配置 `A -> B -> C`，用户选择 B，文生图实际顺序为 `B -> A -> C`。如果 A 不支持编辑，则同一次编辑任务的顺序为 `B -> C`。

任务创建时保存 `api_key_id`、`group_id`、`policy_version`、`selected_model` 和完整 `attempt_plan`。管理员后续修改策略、用户后续调整 Key 或分组不能改变已经创建的任务。创建任务时必须再次确认 API Key 属于当前登录用户且仍处于可用状态，不能信任客户端提交的 user 或 group 字段。

### 8.3 并发更新

管理员更新策略时提交当前 `version`。版本不匹配返回 `409 policy_version_conflict`，前端重新加载并要求管理员确认，不允许最后写入者静默覆盖。

## 9. 项目与数据模型

### 9.1 `image_canvas_projects`

- `id`：ULID 或项目现有统一 ID 类型；
- `user_id`：项目所有者；
- `name`；
- `document`：规范化 JSONB 画布快照；
- `version`：乐观并发版本；
- `thumbnail_asset_id`：可空；
- `created_at`、`updated_at`、`deleted_at`。

`document` 保存节点类型、位置、尺寸、连接、提示词和资产 ID，不保存 Base64、对象存储签名 URL、上游凭证、管理员策略或不可验证的任意 HTML。

### 9.2 `image_assets`

- `id`、`owner_user_id`、`project_id`；
- `source_type`：upload、generated、derived；
- `object_key`、`thumbnail_object_key`；
- `mime_type`、`width`、`height`、`byte_size`、`sha256`；
- `origin_job_id`、`parent_asset_ids`；
- `created_at`、`deleted_at`。

资产删除先进入逻辑删除和延迟清理。只要仍被项目或未过期任务引用，就不得删除对象。

### 9.3 异步任务扩展

复用异步图片任务表，并补充或关联以下字段：

- `owner_user_id`、`project_id`、`client_node_id`；
- `idempotency_key`、`request_digest`；
- `selected_model`、`policy_version`、`attempt_plan`；
- `successful_model`、`attempt_log`；
- `reserved_amount`、`settled_amount`；
- `cancel_requested_at`。

`attempt_log` 只保存模型、序号、时间、耗时、错误类别和无敏感信息的错误摘要。

### 9.4 模型策略与审计

使用独立策略表和条目表，避免把有序、可审计的模型链塞进无结构系统设置。每次更新在同一事务内递增版本、替换条目并写入管理员审计事件。审计事件保存操作者、旧版本、新版本和结构化差异。

## 10. 登录态 Canvas API

所有端点位于现有 `/api/v1` 登录态路由，使用 JWT 中间件、用户模式守卫和现有管理员合规守卫。最终路由注册遵循项目现有 handler/service/repository 分层。

### 10.1 用户与管理员共用端点

```http
GET    /api/v1/image-canvas/config?api_key_id={api_key_id}
GET    /api/v1/image-canvas/projects
POST   /api/v1/image-canvas/projects
GET    /api/v1/image-canvas/projects/{project_id}
PATCH  /api/v1/image-canvas/projects/{project_id}
DELETE /api/v1/image-canvas/projects/{project_id}
POST   /api/v1/image-canvas/assets
GET    /api/v1/image-canvas/assets/{asset_id}
POST   /api/v1/image-canvas/jobs
GET    /api/v1/image-canvas/jobs/{job_id}
GET    /api/v1/image-canvas/jobs/{job_id}/events
DELETE /api/v1/image-canvas/jobs/{job_id}
```

管理员使用画布时也调用这些用户所有权端点。管理员身份不自动获得查看其他用户私有项目或图片的能力。

### 10.2 项目更新

```json
{
  "version": 12,
  "name": "产品概念图",
  "document": { "schema_version": 1, "nodes": [], "edges": [] }
}
```

成功返回新版本。版本不匹配返回 `409 project_version_conflict` 和当前版本元数据，不自动覆盖。客户端保留本地未保存副本，并提供重新加载或另存为新项目的恢复动作。

### 10.3 创建任务

```json
{
  "project_id": "icp_01K1J9B4M7QZ6R2T8W3X5Y0NPA",
  "client_node_id": "node_product_hero_01",
  "operation": "generation",
  "api_key_id": 42,
  "selected_model": "model-b",
  "prompt": "白色背景上的产品概念图，柔和棚拍光线",
  "input_asset_ids": [],
  "parameters": {
    "size": "1024x1024",
    "n": 1,
    "quality": "high",
    "output_format": "png"
  }
}
```

客户端同时发送 `Idempotency-Key`。幂等范围绑定所选 API Key；同一 Key、同一幂等键和相同请求摘要返回原任务，相同键但不同请求返回 `409 idempotency_conflict`。创建成功返回 `202 Accepted`：

```json
{
  "id": "imgjob_01K1J9D7H2C8V4M6Q0R3T5XYZA",
  "status": "queued",
  "api_key_id": 42,
  "selected_model": "model-b",
  "attempt_plan": ["model-b", "model-a", "model-c"],
  "project_id": "icp_01K1J9B4M7QZ6R2T8W3X5Y0NPA",
  "client_node_id": "node_product_hero_01"
}
```

### 10.4 进度与恢复

事件流只传任务状态、当前阶段、尝试序号、可公开模型名、完成数量和结果资产 ID，不传上游错误原文或对象存储凭证。前端使用能够携带现有 Bearer 凭证的流式 `fetch` 消费 SSE，不使用会迫使 JWT 进入查询参数的原生 `EventSource`。断线后客户端使用带退避的 `GET job` 轮询恢复；刷新页面后根据该项目关联的未完成任务重新订阅。

### 10.5 管理端策略 API

```http
GET /api/v1/admin/image-canvas/model-policy
PUT /api/v1/admin/image-canvas/model-policy
GET /api/v1/admin/image-canvas/model-policy/audit
```

更新请求包含当前版本和完整有序条目。服务端在事务中完成校验、版本递增和审计。

## 11. 任务执行、回退与计费

### 11.1 创建阶段

1. 校验功能开关、用户状态、项目所有权和输入资产所有权。
2. 校验所选 API Key 属于当前用户、状态可用，并固化其当前 group。
3. 校验参数和内容安全前置规则。
4. 读取当前模型策略，并确认用户选择属于该 API Key 分组允许的启用链。
5. 根据 Key 分组和操作能力构造 `attempt_plan`；没有兼容模型时返回 `422 no_compatible_image_model`。
6. 计算所有候选模型执行本次请求的最高预估用户费用，并按所选 Key 的余额、配额或订阅原子预占额度。
7. 在同一业务事务边界内保存任务、API Key/group 快照、策略快照、幂等键和预占记录。
8. 返回 202，由 worker 异步认领。

### 11.2 可回退错误

仅以下错误进入下一个模型：

- DNS、连接和 TLS 等网络错误；
- 上游调用超时；
- 上游 HTTP 429；
- 上游 HTTP 5xx；
- 上游宣称成功但响应中没有可用图片，或图片载荷无法通过基本格式校验。

每个模型最多尝试一次。账号级故障转移仍由现有模型执行器负责；模型级回退只在该模型的账号执行策略已返回最终可回退失败后发生，避免两层调度相互递归。

如果无图片响应同时带有明确的内容安全拒绝或其他业务拒绝标记，必须分类为不可回退错误，不能仅因图片为空而继续调用其他模型。

### 11.3 不可回退错误

以下错误立即终止：

- 请求参数或上传图片无效；
- 未登录、无权限或资源不属于当前用户；
- 额度预占失败；
- 内容安全拒绝；
- 无兼容能力；
- 除 429 外明确的上游 4xx 业务错误。

服务端不得把内容安全拒绝改写成服务错误来绕过模型策略。

### 11.4 保存与结算

成功响应先进入可恢复的结果保存阶段，再完成结算：

1. 校验图片 MIME、尺寸和大小；
2. 写入私有对象存储并创建 `image_assets`；
3. 按 `successful_model` 和实际成功数量计算最终费用；
4. 从预占额度结算一次并释放差额；
5. 原子地把任务标记为 completed；
6. 通知画布插入或恢复结果节点。

上游已经成功但对象存储失败时，任务进入 `saving` 重试，不调用下一个模型。所有模型失败或在可安全阶段取消时，释放全部预占。失败尝试的上游成本由平台承担，不重复向用户收费。

如果进程在已获得上游成功但尚未可靠保存结果时中断，沿用异步图片任务设计的 `indeterminate` 语义，禁止自动再次生成，直到恢复流程能够确定结果状态。

### 11.5 取消

取消请求设置 `cancel_requested_at`。尚未执行的任务直接取消并释放预占；回退间隙停止发起下一模型；已经发给上游的请求尽力取消，但无法保证撤销上游成本。取消后到达的结果不向画布发布，清理策略按孤立资产处理。

## 12. 安全与隐私

- 画布从不接收上游账号密钥或 Provider URL。
- 所有项目、任务、输入图和输出图查询都按 `owner_user_id` 进行服务端授权，不能只依赖前端隐藏。
- 上传校验 MIME、文件签名、尺寸、像素数和文件大小；对象键由服务端生成，不能接受用户路径。
- 图片下载使用鉴权代理或短时签名 URL，并设置适当的 `Content-Disposition`、`Content-Type` 和缓存策略。
- JSONB 画布文档使用版本化 schema 和允许字段校验，不保存任意脚本或 HTML。
- React 微前端与 Vue 宿主遵循同一 CSP；构建不得引入运行时远程脚本。
- 日志、事件流和审计中不记录 Authorization、上游密钥、完整原始私密图片或签名下载 URL。
- 管理员只能配置模型标识和顺序，不能通过该页面写入任意上游 URL。

## 13. AGPL-3.0 合规边界

直接派生的 React 画布及与其组成同一前端程序的修改按 AGPL-3.0 处理。发布检查至少包含：

1. 保留上游版权和许可证声明；
2. 在修改文件和发行说明中标注 Sub2API 修改及日期；
3. 在交互界面的“关于/源码”入口显示版权、无担保提示、许可证和获取源码方式；
4. 向通过网络使用修改版画布的用户提供该版本的完整对应源码；
5. 对应源码包含构建和安装所需脚本，不只提供压缩后的静态产物；
6. 每个生产构建记录上游基线、Sub2API 提交和可下载源码地址；
7. CI 在源码地址未配置或许可证文件缺失时阻止启用画布功能。

后端与既有 Sub2API 代码的最终许可证组合方式必须在发布前由项目维护者或法律专业人士确认。为了降低边界歧义，React 微前端保留独立包、独立许可证清单和清晰的构建产物目录，但不能把这种工程隔离当成规避 AGPL 网络条款的依据。

## 14. 可观测性与审计

指标至少包括：

- 按模型和操作统计的任务数量、成功率和延迟；
- 每个 attempt position 的成功率；
- 按错误类别统计的回退次数和全链失败次数；
- 排队、执行、保存和结算各阶段耗时；
- 预占金额、结算金额和释放金额不一致告警；
- 项目保存冲突、事件流断线和轮询恢复次数；
- 对象存储失败和孤立资产数量。

管理员任务详情可查看所选模型、策略版本、尝试顺序、每次耗时、脱敏错误类别、成功模型和最终费用。普通用户只看到完成当前操作所需的信息，不看到账号、Provider 或内部错误原文。

管理员修改模型链必须写入现有审计体系。项目内容和图片不进入通用审计事件正文。

## 15. 数据迁移、发布与回滚

### 15.1 数据库迁移

迁移只新增表、索引和可空关联，不重命名或删除现有图片、用量和账号字段。首次部署时 `image_canvas_enabled=false`，模型策略未配置，用户和管理员入口均不可用。

### 15.2 发布顺序

1. 部署后端表结构、repository、service、handler 和 worker，保持功能关闭；
2. 部署 React 微前端产物、Vue 宿主页、路由、菜单和许可证页面；
3. 管理员配置并保存模型链；
4. 在非活动蓝绿环境执行权限、对象存储、额度和真实小额生图冒烟测试；
5. 开启候选环境功能开关并验证用户和管理员路由；
6. 获得独立维护窗口确认后，通过 HAProxy 切换生产流量；
7. 观察任务成功率、回退率、结算和存储指标后再扩大使用。

数据库迁移必须兼容切换前后的应用版本，避免切回旧版本时无法启动。

### 15.3 回滚

先关闭功能开关，阻止新任务和菜单入口，再让运行中任务完成或进入可恢复终态，然后切回旧应用版本。新增表、项目、任务和对象存储资产保留，不在紧急回滚中执行破坏性 down migration。修复版本重新上线后可以恢复项目。

本设计不改变当前生产 HAProxy 状态，也不授权执行首次切流。

## 16. 测试策略

### 16.1 后端单元测试

- `A -> B -> C` 下选择 A、B、C 的顺序构造；
- 禁用项、重复项和能力不兼容项过滤；
- 网络、超时、429、5xx 和空图片响应触发回退；
- 参数错误、内容安全、额度和其他 4xx 不触发回退；
- 策略版本和项目版本冲突返回 409；
- 幂等键相同请求复用、不同请求冲突；
- 预占最高估价、按成功模型结算和释放差额；
- 全失败、取消、保存重试和 indeterminate 不重复扣费；
- 用户所有权与管理员策略权限。

### 16.2 集成测试

使用可编程假 Provider 覆盖：

- 主模型超时、第二模型 429、第三模型成功；
- 某模型内部账号故障转移结束后才进入下一模型；
- 内容安全拒绝后零次额外调用；
- 上游成功但对象存储暂时失败时只重试存储；
- worker 重启、重复投递和取消竞态；
- SSE 断线后查询接口恢复；
- 多标签项目保存冲突；
- 上传、下载和跨用户资产访问。

### 16.3 前端测试

- Vue 用户和管理员路由守卫、菜单开关与标签页；
- React `mount/updateContext/unmount` 生命周期和资源清理；
- 项目创建、自动保存、冲突恢复、删除和跨设备重新加载；
- 节点创建、连接、复制、删除、撤销和重做；
- 模型能力过滤、回退状态和实际成功模型显示；
- 管理员添加、启停、拖拽排序、版本冲突和审计入口；
- 中英文、亮暗主题和错误文案布局。

### 16.4 端到端与视觉验证

Playwright 覆盖用户文生图、图片编辑、连续分支、刷新恢复、下载，以及管理员配置和管理员画布。桌面和移动视口都要截图验证：

- 画布非空且节点、连线和生成图片实际渲染；
- 全局侧栏、画布工具条、节点和底部生成面板无重叠；
- 最长中英文错误文本不会溢出按钮或遮挡后续内容；
- 缩放、拖拽、触控和路由切换可用；
- “关于/源码”入口和许可证内容可访问。

## 17. 验收标准

1. 开启功能后，普通用户能从左侧“图片生成”进入完整画布，管理员能从管理端左侧进入带“生成画布”和“模型配置”的页面。
2. 浏览器网络请求、存储和页面源码中不存在上游账号密钥或可由用户修改的 Provider URL。
3. 管理员可以配置一个主模型和多个有序兜底模型，重复或无效配置不能保存。
4. 用户必须主动选择自己名下的可用 API Key，不能查看或使用他人的 Key，画布不显示密钥明文。
5. 用户只能选择全局链中被所选 Key 分组允许的模型；选择 B 时，B 优先且其他兼容模型保持管理员顺序。
6. 只有已确认的服务错误触发回退；内容安全和业务 4xx 不回退。
7. 用户只按最终成功模型和实际图片数结算一次，失败或取消释放预占，账单归属于所选 Key。
8. 项目和图片服务端持久化，用户换设备登录后可以继续编辑，且不能访问他人资源。
9. 对象存储失败、任务重投和页面刷新不会自动重复生成或重复扣费。
10. 现有同步图片端点和其他 AI 功能的回归测试通过。
11. 桌面和移动端画布可操作、图片可见、控件无重叠。
12. 发布产物提供与运行版本一致的 AGPL 许可证、修改声明和对应源码入口。
13. 功能可通过开关关闭并通过蓝绿部署回滚，不删除用户画布数据。

## 18. 实施依赖与顺序约束

本功能依赖 `2026-07-24-async-images-codex-design.md` 中的 Image Executor、Image Job Service 和 Image Object Store。实施计划不得在画布模块中复制这些基础设施。如果异步图片计划尚未落地，应先实现其服务端基础部分，再依次实现模型策略、Canvas API、Vue 宿主、React 画布适配和端到端发布验证。

当前主工作区存在尚未提交的图片模型回退和调度修改。实施时必须在隔离工作树中基于最新目标分支工作，并在修改调度器前审阅和整合这些变更，不能覆盖或回退用户现有工作。
