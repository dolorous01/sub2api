# HAProxy 蓝绿部署设计

日期：2026-07-31
状态：已确认，待实施计划

## 1. 背景

当前生产请求链路为：

```text
Internet
  -> Cloudflare Tunnel
  -> Python 路径代理 :8080
  -> 单个 Sub2API 容器 :18080
  -> PostgreSQL :5432
  -> Redis :6379
```

Sub2API 只有一个实例。更新镜像或重建容器时，旧实例退出到新实例就绪之间没有可用后端，AI 请求会失败；正在进行的 SSE 或 WebSocket 流式请求也会被中断。

生产服务器只有 2 核 CPU 和约 1 GB 内存，已经使用较多 Swap。因此生产机不得执行源码编译，蓝绿实例只在发布和排空期间短暂并行。

## 2. 目标

- 首次接入 HAProxy 允许一次约 5 到 15 秒的计划切换窗口。
- 接入完成后的计划内发布不主动中断已有 AI 流式请求。
- 新版本未通过健康检查和冒烟测试时不得接收用户流量。
- 发布失败时保留旧版本，并支持自动回退或一条命令回滚。
- PostgreSQL、Redis 和 Cloudflare Tunnel 不因应用发布而重启。
- 镜像在外部 CI 构建，生产服务器只拉取不可变镜像。
- 方案适配当前单机和 1 GB 内存限制，不引入 Kubernetes。

## 3. 非目标

- 本次不提供整台服务器故障时的高可用；该能力需要第二台服务器和外部负载均衡。
- 本次不移除现有 Python 路径代理。
- 本次不复制 PostgreSQL、Redis 或 Cloudflare Tunnel。
- 本次不允许破坏性数据库迁移与旧版本同时运行。

## 4. 目标架构

```text
Internet
  -> Cloudflare Tunnel
  -> Python 路径代理 :8080
  -> HAProxy 127.0.0.1:18080
       |-- sub2api_blue  127.0.0.1:18081
       `-- sub2api_green 127.0.0.1:18082
              -> PostgreSQL 127.0.0.1:5432
              -> Redis 127.0.0.1:6379
```

### 4.1 HAProxy

- 以系统服务运行，并启用 master-worker 模式和优雅重载。
- 只监听 `127.0.0.1:18080`，不直接暴露公网。
- 同时配置 Blue 和 Green，一个为 primary，另一个为 backup。
- 使用 HTTP 健康检查访问 `/health`。
- 使用本地 Unix Socket 提供状态查询，Socket 权限限制为管理员和部署用户可用。
- 不配置会强制终止长连接的短 `hard-stop-after`。
- 为 SSE 和 WebSocket 设置足够长的 client、server 和 tunnel 超时。

### 4.2 Sub2API 实例

- Blue 固定使用 `SERVER_HOST=127.0.0.1`、`SERVER_PORT=18081`。
- Green 固定使用 `SERVER_HOST=127.0.0.1`、`SERVER_PORT=18082`。
- 两个实例共享现有 PostgreSQL、Redis、密钥和业务配置。
- 平时只有活动实例运行；备用实例通常停止，只在发布和回滚时启动。
- 容器日志写标准输出，并配置 Docker 日志轮转，避免两个进程争用同一日志文件。

### 4.3 镜像和 CI

- GitHub Actions 负责运行测试、构建前后端和生成 Docker 镜像。
- 镜像推送到 GHCR，标签使用 Git commit SHA，不使用 `latest` 部署生产。
- 生产部署需要显式批准，不因主分支提交自动切换生产流量。
- 部署脚本验证容器实际镜像摘要与目标版本一致。

## 5. 发布流程

### 5.1 发布前检查

部署脚本使用 `flock` 防止并发发布，并执行以下检查：

- 当前公网入口、HAProxy、活动实例、PostgreSQL 和 Redis 健康。
- HAProxy 当前 primary、backup 与记录的活动颜色一致。
- 目标镜像标签存在、可拉取且不是 `latest`。
- 可用内存、Swap 变化和磁盘空间达到演练确定的安全阈值。
- 数据库迁移文件是否变化；如有变化，先完成数据库备份。

任一前置检查失败都终止发布，不修改 HAProxy，不停止活动实例。

### 5.2 启动和预热备用实例

1. 确定非活动颜色及其固定端口。
2. 拉取目标 commit SHA 镜像。
3. 使用现有生产配置启动非活动实例，但保持其 HAProxy backup 身份。
4. 连续多次检查直接端口 `/health`。
5. 验证容器镜像摘要、数据库和 Redis 连接。
6. 执行只读 API 冒烟测试。
7. 可选使用专用测试密钥执行一次低消耗 AI 请求。

任何检查失败都停止备用实例，并保持当前流量路径不变。

### 5.3 流量切换

切换通过生成新的 HAProxy 配置完成：新实例成为 primary，旧实例成为 backup。

1. 将新配置写入临时文件。
2. 使用 `haproxy -c` 完整校验配置。
3. 原子替换正式配置。
4. 通过 systemd 平滑重载 HAProxy。
5. 仅在重载和入口健康检查成功后更新活动颜色状态文件。

平滑重载后，新 HAProxy 工作进程把新请求发送到新实例；旧工作进程不再接收新连接，但继续服务切换前已建立的 SSE、WebSocket 和普通 HTTP 请求。

### 5.4 观察和连接排空

- 在观察期内保留旧实例作为 backup。
- 监控 HAProxy 新 primary 健康、5xx、活动连接、容器内存和关键日志。
- 监控旧 HAProxy 工作进程和旧实例连接数。
- 只有旧连接连续 30 秒为零且新实例观察期通过，才停止旧实例。
- 如果长连接一直不结束，发布暂停并告警，不强制停止旧实例。
- 停止旧实例后保留上一版镜像和部署记录，用于后续回滚。

## 6. 失败处理和回滚

| 失败阶段 | 处理方式 |
| --- | --- |
| 镜像拉取失败 | 终止发布，活动实例继续服务 |
| 备用实例启动失败 | 停止备用实例，不切流量 |
| 健康检查或冒烟测试失败 | 停止备用实例，不切流量 |
| HAProxy 配置校验失败 | 不替换配置、不重载 HAProxy |
| HAProxy 重载失败 | 恢复旧配置并确认旧入口健康 |
| 新 primary 在观察期异常 | HAProxy 使用旧 backup 接收新请求，部署脚本恢复旧配置 |
| 旧实例排空超时 | 保留双实例并告警，不强制停止 |
| 旧实例已停止后需要回滚 | 重新启动上一版镜像，健康后平滑切回 |

回滚只切换应用版本，不自动执行数据库反向迁移。只有向后兼容的数据库变更才允许进入蓝绿发布。

## 7. 数据库和共享状态

### 7.1 迁移规则

Sub2API 启动时会自动执行 SQL 迁移，迁移器已有 PostgreSQL advisory lock，可防止两个实例并发执行同一迁移。但该锁不能保证新旧应用版本兼容。

数据库变更必须采用 expand-migrate-contract：

1. Expand：增加新表、字段或索引，旧版本仍可运行。
2. Migrate：迁移数据并发布兼容新旧结构的代码。
3. Contract：确认旧版本不会再运行后，在后续版本删除旧结构。

蓝绿发布中禁止直接执行：

- 删除或重命名旧字段。
- 缩小字段类型。
- 新增无默认值的强制非空字段。
- 会长时间锁表的普通索引创建。
- 让旧版本无法读取的数据格式变更。

迁移文件发生变化时，部署前创建 PostgreSQL 备份。事务迁移失败时新实例不得启动；非事务迁移部分失败时暂停发布并由管理员检查，不自动猜测回滚 SQL。

### 7.2 后台任务

项目已有 PostgreSQL/Redis leader lock、缓存失效和多实例相关机制，但实施前仍须验证所有关键后台任务。双实例并行期间不得出现重复扣费、重复支付处理、重复清理或相互覆盖的定时任务。

## 8. 首次接入流程

首次改造接受约 5 到 15 秒的计划切换窗口：

1. 备份生产 Compose、配置文件和数据库。
2. 安装并配置 HAProxy，但暂不占用 `18080`。
3. 使用当前已知正常的生产镜像启动 Blue，监听 `18081`。
4. 直接验证 `18081/health`、只读 API 和 AI 冒烟测试。
5. 在低流量时段确认当前活动请求尽量接近零。
6. 停止占用 `18080` 的旧 `sub2api_core`。
7. 启动 HAProxy，使 `18080` 转发到 Blue `18081`。
8. 验证 `8080/health`、登录、管理端和 AI 请求。
9. 如验证失败，停止 HAProxy 并恢复原 `18080` 容器。

首次接入不重启 PostgreSQL、Redis、Python 路径代理或 Cloudflare Tunnel。

## 9. 测试方案

### 9.1 静态和组件测试

- HAProxy 配置语法检查。
- 部署脚本单元测试或可重复的沙箱测试。
- Docker Compose 配置检查。
- 数据库迁移兼容性测试。
- 镜像构建、启动和健康检查。

### 9.2 发布演练

- Blue 和 Green 分别启动并通过检查。
- 备用实例不接收正常用户流量。
- 模拟备用实例启动失败，活动实例保持可用。
- 执行 Blue 到 Green，再从 Green 回滚到 Blue。
- 切换后终止新 primary，验证旧 backup 接管。
- 双实例短暂运行时监控内存、Swap 和 OOM 事件。
- 验证后台任务没有产生重复业务副作用。

### 9.3 长连接测试

切换期间持续运行：

- 一条较长的 SSE/AI 流式请求。
- 一条 WebSocket 请求。
- 一组普通并发 HTTP 请求。

必须验证原有长连接在旧实例完成，新请求进入新实例，HAProxy 不缓存完整流式响应，旧连接归零前旧实例不会停止。

## 10. 监控和审计

- HAProxy 后端状态、活动连接、旧工作进程和 5xx。
- Blue/Green 容器健康、内存和重启次数。
- `8080/health` 与当前 primary 的直接健康检查。
- PostgreSQL 和 Redis 健康。
- Docker 日志大小、磁盘剩余空间和 Swap 变化。
- 部署目标 SHA、开始时间、切换时间、排空时间和回滚结果。
- 每次生产变更继续记录到现有生产变更日志。

## 11. 验收标准

- 首次 HAProxy 接入窗口不超过约 15 秒。
- 后续计划内发布演练中测试请求零失败。
- 发布时已有 AI 流式连接不被部署流程主动中断。
- 新实例未通过全部检查时不能接收用户流量。
- 旧实例活动连接未归零时不能停止。
- 在旧实例仍运行的观察期内，新版本异常时旧 backup 能接管新请求。
- 发布失败能自动或通过一条命令切回旧版本。
- 发布过程不重启 PostgreSQL、Redis 和 Cloudflare Tunnel。
- 生产服务器不执行源码编译。
- 双实例并行不触发 OOM，后台任务不产生重复业务副作用。

## 12. 已知限制

- 单机蓝绿部署只能消除计划发布造成的应用停机，不能抵御整台服务器、宿主网络或磁盘故障。
- HAProxy 健康检查发现非计划崩溃前，极少量正在发往故障 primary 的请求仍可能失败；本设计的零中断目标针对计划内发布。
- 1 GB 内存余量有限。资源门禁失败时必须放弃本次发布，不能为了完成发布而强行运行双实例。
